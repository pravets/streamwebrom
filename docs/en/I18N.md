# Languages

[Español](../I18N.md) · **English**

The studio interface is published in **Spanish, English and Russian**. Spanish is
the source language and the **fallback**: if a translation is missing or a key is
misspelled, the Spanish text is still shown instead of leaving a gap or a raw key
on screen.

## How it works

Everything lives in the browser, with no dependencies and no build step:

- `web/js/i18n.js` — core: `t(key, variables)`, `installI18n()`, `setLang()`,
  `lang()`, `onLangChange(fn)`. Resolves `{name}` and picks the plural form
  (`one` / `few` / `many` / `other`) when the value is an object and `{n}` is
  passed.
- `web/js/i18n/es.js`, `en.js`, `ru.js` — assemble the objects for each area.
- `web/js/i18n/<language>/<area>.js` — the texts, grouped by screen
  (`studio`, `guest`, `home`, `devices`, `effects`, `diagnostics`, `pages`, `misc`,
  `studiojs`, `common`).

The language is chosen in this order: `?lang=es|en|ru` → what is stored in
`localStorage["swr.lang"]` → `navigator.languages` → Spanish. The `[data-lang-picker]`
selector is mounted only inside each `[data-lang-slot]`, stores the choice and emits
`swr:lang` so dynamic views repaint their labels.

## Marking strings

In the HTML the Spanish text stays written in the markup and only the attribute is
added, so without JavaScript (or with a nonexistent key) the page remains
readable:

```html
<h1 data-i18n="home.heroTitle">Tu estudio en vivo.</h1>
<button data-i18n-title="studio.saveRoom" title="Guardar sala">Guardar sala</button>
<input data-i18n-placeholder="home.roomPlaceholder" placeholder="Mi show en vivo">
```

Available attributes: `data-i18n` (text), `data-i18n-title`, `data-i18n-aria`,
`data-i18n-placeholder`.

In JavaScript:

```js
import { t, onLangChange } from "./i18n.js";

label.textContent = t("studio.sourceCount", { n: count });
onLangChange(() => label.textContent = t("studio.sourceCount", { n: count }));
```

Constants with labels are not translated at import time: they store the key or are
built in a function, and whatever stays fixed on screen is repainted inside
`onLangChange`.

Plural strings (an object in all three languages, with `{n}` in the text):

```js
// es
"studio.sourceCount": { one: "{n} fuente", other: "{n} fuentes" },
// en
"studio.sourceCount": { one: "{n} source", other: "{n} sources" },
// ru
"studio.sourceCount": { one: "{n} источник", few: "{n} источника", many: "{n} источников" },
```

Proper names and technical terms are not translated: StreamWebRom, OBS, YouTube,
Twitch, Kick, Cloudflare, WebRTC, WHIP, WHEP, PiP, SFU, Backstage, names of
devices that come from the browser, ids, classes, URL parameters and storage
keys.

## Tests

```bash
node --test tests/i18n.test.mjs
```

It checks that all three languages have exactly the same keys, that no
translation is empty, that the plural forms are complete, the language detection
order, the Russian plurals and that every key used in the HTML exists.
The browser smokes set `locale='es-ES'` (and `?lang=` when needed) so that the
Spanish assertions keep holding.

## Server errors

The server responds with the usual Spanish text and a stable `code` beside it:

```json
{"error": "La sala está llena", "code": "room_full"}
```

Signaling messages (`type: "error"`) carry the same field. The browser
translates by `code` (`server.<code>` in the dictionaries) and, if the server is
newer and sends a code this build does not know, shows the text as is. Codes are
created in Go with `studio.Userf("room_full", "La sala está llena")`; internal
errors carry no code and are never translated.

`tests/i18n.test.mjs` walks `internal/` and fails if a server code has no
translation or if an entry that the server no longer sends is left over.
