# Connecting from 4G/5G and other networks

[Español](../REDES-MOVILES.md) · **English** · [Русский](../ru/MOBILE-NETWORKS.md)

If a phone joins over Wi-Fi and fails when using mobile data, check the web/signaling and the audio/video transport separately. Loading the HTTPS page does not prove that a WebRTC path exists.

## What 1.5.1 fixes

Previously a single SDP description was sent, after a maximum of 2 seconds in the browser and 3 seconds on the server. Candidates discovered later never reached the other end. Now the browser and the SFU exchange candidates through **trickle ICE**, also after sending the SDP. Negotiations are isolated per socket and identifier.

The guest sees "Connecting audio and video" until WebRTC actually connects. If there is no path within 30 seconds an error appears and they can press **Retry audio and video**. Signaling has its own 20-second timeout. Losing it cancels the negotiation and allows reconnecting without leaving pending operations.

In 1.6.0 the SFU also announces `a=ice-options:trickle` in the WebSocket offers and answers. Sending candidates in messages without announcing this capability in the SDP could make the browser declare a failure when the first private paths were unreachable, before receiving the TURN candidate. WHIP/WHEP keep their negotiation without trickle.

## The infrastructure requirement

**STUN discovers addresses; TURN relays the traffic when there is no direct connection.** Some mobile networks use NAT or filters that prevent a direct path. Changing timeouts or adding more STUN does not replace a relay.

Cloudflare Tunnel publishes the web and the WebSocket. The HTTP tunnel used by StreamWebRom does not provide a relay for audio/video. Forwarding UDP 50000 helps with direct paths, but does not guarantee access from every mobile network.

You need a **managed TURN service** or a coturn server on a machine/VPS with a public IP. For networks that block UDP, the service must offer TURN over TCP and preferably TLS on 443. Use the addresses and credentials that service provides. Do not reuse an HTTPS URL from the tunnel as if it were TURN.

## Configuring on Windows

1. Run the current launcher. In the **Network** card, fill in **TURN relay**, **User** and **Password** for a provider with fixed credentials.
2. In TURN relay, enter the URLs delivered by your provider, separated by commas. Example for guidance: `turn:relay.ejemplo.com:3478?transport=udp,turn:relay.ejemplo.com:3478?transport=tcp,turns:relay.ejemplo.com:443?transport=tcp`. Replace the domain; the example is not a real service.
3. Press **Apply and restart** when there is no broadcast in progress. The password is encrypted with your Windows user; it is not added to the command line or the registry.
4. On the phone, turn off Wi-Fi and open `/diagnostics` on your domain. Press **Test TURN relay**. It must report that it obtained a TURN path.
5. Enter the backstage and check image and audio in both directions. The TURN allocation test on its own does not replace this check.

## Configuring the server by environment

```text
SWR_TURN=turn:relay.ejemplo.com:3478?transport=udp,turns:relay.ejemplo.com:443?transport=tcp
SWR_TURN_USER=usuario-entregado-por-el-servicio
SWR_TURN_PASS=credencial-entregada-por-el-servicio
```

Configure those variables in the service that runs StreamWebRom and restart it. There are also `-turn`, `-turn-user` and `-turn-pass`; the environment keeps the password off the command line. The relay access credentials are delivered to the WebRTC clients so they can connect; use your TURN service's quotas and credential control.

## Reproducible validation

`scripts/browser-smoke.py` removes candidates from the SDP and delays the ICE messages of both ends by 3.5 seconds. It checks real video, admission to the backstage, a total ICE block with a visible error, the retry, and reconnection without reloading.

`scripts/relay-smoke.py` forces publishing and receiving with `iceTransportPolicy: relay`, checks decoded video frames and requires the selected candidate to be `relay` with TCP transport. The `scripts/turn-smoke-server.go` fixture listens only on loopback and uses test credentials; **it is not a production server**. CI runs both tests.

These tests do not represent a check against every mobile carrier.

## Alternative paths per participant (1.6.1)

Since 1.6.3 the guest starts in automatic mode. On pressing Enter, and before joining or calling the backstage, video generated by Cloudflare TLS/443 is checked. If it fails, the local relay is checked and the one that works is chosen. The guest is not asked to change options after a failed join. Each attempt has a 12-second deadline; if both fail this is reported before entering. Installations without TLS relays keep their usual direct connection.

The test does not open the camera or microphone and uses a separate temporary room, limited and with an expiry. The manual options are only shown when opening "Advanced connection options". Each visit starts automatically, also from guest links that kept `network=tls` or `network=local`; those parameters still select the corresponding test in `/diagnostics`.

To verify carriers and technologies without confusing a laboratory test with a real network, use the [carrier matrix and protocol](OPERATOR-TESTS.md).

Since 1.6.2 pages load JavaScript/CSS through content-hashed paths, including imports between modules and the service worker. This prevents a new page from using old code retained by the browser or the CDN. After updating, reload the page before testing. A visible button that does not respond may indicate a mix of versions; the number from `/api/config` on its own does not confirm which JavaScript the phone loaded.

A TURN allocation test can pass and audio/video can still fail. In `/diagnostics`, "Test video to the server" sends a generated image and verifies its reception and decoding. It does not open the camera or the microphone.

To check each transport separately, try the "Encrypted connection over 443 only" and "Host machine relay over 443" options in diagnostics. In the guest's advanced options, the "Connection" selector lets you force a path for that visit. The automatic selection before entering is the normal behavior.

`tls` excludes STUN, direct connections and TURN/UDP: it only uses `turns:` over TCP/443. `local` uses the TURN installed by the host and also uses TLS/443 from the browser. The SFU offers its direct candidates to reach that relay, even if Cloudflare stays active for other participants. There is no need to disable Cloudflare globally or wait for the usage cutoff. These paths require a valid TLS/443 relay; server URLs provided by the guest are not accepted.

Compatibility with a specific carrier must be confirmed on that phone and with its mobile data. A test from another network does not confirm the connectivity of Movistar Chile. It is not necessary to change the APN, disable IPv6 or share passwords to test these alternatives.

## Cloudflare and local fallback (1.6.0)

On Windows, **Network → Local TURN / Cloudflare** configures both. The tokens are stored with DPAPI in `relay-credentials.json`, inside the user's data folder. Do not copy this file to another user or publish the tokens. The launcher passes them to the server through the environment, without including them in arguments or logs. Linux/macOS use the variables listed below and a service secret store.

Cloudflare requires a Realtime subscription accepted by the account holder, a dedicated TURN app and an **Account Analytics Read** token limited to that account. The master TURN key is only used in the backend. Browsers receive temporary credentials; they do not receive the master tokens.

When Cloudflare is active, the SFU uses that provider's public relay candidates. This also works if the machine's router does not support valid redirections; it prevents the first private paths from causing a failure before the relay candidate arrives. Switching to local restores the policy that allows direct paths to the SFU. This counts server-side traffic within TURN usage.

The server queries every 30 seconds the TURN egress bytes of **all keys in the account**. The highest observed value and the monthly cutoff are stored in `data/turn-quota.json`, including the names of issued credentials so they can be revoked after a restart. Do not delete that state to reset the counter. The first check happens before accepting clients. An analytics, credential generation or state write error selects the local relay. The cutoff persists until the next UTC month, even if a later reading gives a lower value.

Since v1.10.1, if that file is damaged or cannot be read, the web starts with the local relay and Diagnostics shows "usage record unavailable; Cloudflare paused". The file is kept intact and no Cloudflare credentials are issued. This pause is also maintained when changing month or restarting while the record is still damaged. Save a private copy, restore a valid verified record without lowering the maximum usage or losing an active cutoff or credentials pending revocation, and restart the server. If there is no reliable copy, continue with the local relay and review usage and credentials in the account before re-enabling Cloudflare. The local relay must be reachable so that guests can send audio and video.

It also keeps a persistent local estimate while Cloudflare is active: it counts RTP received by the SFU and sent to its subscribers, adds 64 bytes per packet and applies a 2× margin. At each check it takes the greater of the previous estimate and analytics, and adds the pending local traffic. This estimate may count traffic in excess and bring the cutoff forward; it avoids depending solely on Cloudflare's update. It does not include exact billing control, other uses of the account or all possible forwardings/protocols; the 100 GB margin and the warning about charges are retained. Local fallback traffic does not increase this estimate.

The default preventive cutoff is **900 decimal GB**. Cloudflare offers 1,000 GB/month shared between TURN and SFU; after that it charges for additional traffic. This control measures TURN and leaves a margin: **it is not a billing limit and does not guarantee zero cost**. Analytics may be delayed or sampled and the use of other Realtime products reduces the shared balance. If you use Cloudflare's SFU/WebSocket adapter separately, lower the cutoff to reserve that usage. To avoid any possibility of provider charges, disable Cloudflare and use only the local relay.

When the cutoff is reached, the server stops offering Cloudflare, attempts to revoke the credentials still valid and retries failed revocations on the following checks. Reconnect the browsers so that active connections also change path. There may be a brief interruption; WHIP/WHEP are closed and their clients must reconnect. Recordings and live outputs may need resuming. Credentials are renewed at 12 hours (24-hour validity), also with reconnection. An unreachable revocation API may delay the withdrawal of credentials used outside this application until they expire.

### Local relay with direct ports

The native TURN only relays to this machine's IPs and the **SFU's fixed UDP port**. It does not allow using it as a general proxy to the internet/LAN. Configure a stable public IP or update its address when it changes; reserve the LAN IP in the router's DHCP.

- Listener: `0.0.0.0:3478`, UDP and TCP. Announced IP: the real public IPv4.
- Allocation range: UDP `49160–49223` (64 simultaneous allocations at most, shared by publishing/receiving connections).
- Open/forward those ports to the machine and the media UDP (normally 50000). An additional TCP listener is optional.
- `turn:IP:443?transport=tcp` uses TCP without TLS. For TLS you need a terminator with a valid certificate and a `turns:` URL. Do not confuse the two transports.

Testing from the LAN itself does not check public access. Verify allocation **and real video** from another connection before relying on this fallback. If there is CGNAT or the router does not allow correct redirections, the direct listener is not enough.

### Local relay behind Tailscale Funnel

It is an optional alternative for publishing the local listener with TLS when the router prevents opening ports. It requires Tailscale installed/connected, Funnel enabled by the account holder and a domain from their tailnet. Funnel has bandwidth limits: check capacity and stability for your program.

```text
tailscale funnel --bg --tls-terminated-tcp=443 tcp://127.0.0.1:13478
```

Keep other Tailscale services; do not use `serve reset` or replace occupied ports. TURN configuration for **SFU and relay running on the same machine**:

```text
SWR_RELAY_LISTEN=127.0.0.1:13478
SWR_RELAY_PUBLIC_IP=127.0.0.1
SWR_RELAY_URLS=turns:TU-EQUIPO.TU-TAILNET.ts.net:443?transport=tcp
SWR_RELAY_SECRET=SECRETO_ALEATORIO_DE_AL_MENOS_32_BYTES
SWR_RELAY_MIN=49160
SWR_RELAY_MAX=49223
SWR_UDP_PORT=50000
```

Here the allocation address is loopback because the SFU that sends/receives the packets is on the same machine. The browser reaches the relay through TLS via Funnel. The relay and SFU UDP stay local; it does not need to be published on the router. Do not use that loopback address with an SFU located on another machine. The example domain must be replaced with yours.

### Variables for Cloudflare

```text
SWR_CF_ACCOUNT=ID_DE_CUENTA
SWR_CF_TURN_KEY_ID=ID_DE_CLAVE_TURN
SWR_CF_TURN_KEY_TOKEN=TOKEN_MAESTRO_TURN
SWR_CF_ANALYTICS_TOKEN=TOKEN_ACCOUNT_ANALYTICS_READ
SWR_CF_TURN_BUDGET=900000000000
```

Configuring the local relay as well is required. In **Diagnostics**, "TURN provider" indicates Cloudflare or local machine. The test button only confirms an allocation; also check backstage, audio and video from mobile data. `relay-connectivity` lets you run the video test from an external runner against the published installation; it does not require Cloudflare secrets in GitHub.

### Reconnecting after an interruption

Since 1.6.4, the "Reconnect" button cancels the previous session, rechecks the paths and restores the complete connection without reloading the page. It keeps the re-entry permission, the password in memory and the active devices with their mute state. If the server restarted and no longer recognizes the permission, the host may have to admit the guest again. It does not restore permissions revoked by an ejection.

Since 1.6.6, the "Sign in again" link on the "You left the room" screen opens a new document keeping the invitation. It no longer gets stuck in a navigation to the same `#invite` fragment. Afterwards the entry screen appears again.
